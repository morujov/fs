## 3. Найдено и **исправлено**

### 3.1. Планировщик не запускался вообще — cron не был установлен ⚠️ критично
`php artisan schedule:list` показывал три задачи, но `cron` в системе
отсутствовал, и **ни одна из них не выполнялась**:

- `listings:expire` (10:04 ежедневно) — объявления никогда не истекали бы;
- `data:prune` (03:30 по воскресеньям) — **GDPR-удержание не работало**
  (инвариант №12: персональные данные не хранятся вечно). Для проекта в ЕС
  это не «не работает функция», а нарушение ст. 5 GDPR;
- `queue:work` — очередь не разбиралась.

**Исправлено:** установлен `cron`, добавлено правило `/etc/cron.d/numeros-es`.
Проверено не на словах: подождал минуту — планировщик отработал сам дважды,
лог пишется в `/var/log/numeros-schedule.log`.
`data:prune --dry-run` отрабатывает штатно и показывает таблицу к очистке.

### 3.2. Тесты уходили в боевую базу ⚠️ критично, риск потери данных
`php artisan test` на сервере подключился к **`numeros_es`** — боевой базе
стенда, — а не к `numeros_es_testing`. Причина: при закэшированном конфиге
(`config:cache`, а на сервере он закэширован всегда) Laravel читает
`bootstrap/cache/config.php` и **не смотрит на `<env>` из `phpunit.xml`».
`RefreshDatabase` делает `migrate:fresh`, то есть дропает таблицы: один
неудачный запуск тестов — и данные клиента снесены.

В этот раз пронесло (прогон упал на дублях уникального индекса, 487 объявлений
уцелели), но это везение, а не защита.

**Исправлено, двумя правками в репозитории:**
- `tests/TestCase.php` — предохранитель: если имя базы не кончается на
  `_testing`, прогон останавливается с внятным сообщением. Проверено — блокирует.
- `phpunit.xml` — убраны прибитые `DB_USERNAME=root` / `DB_PASSWORD=`
  (на сервере другой пользователь БД); теперь берутся из `.env`,
  фиксируется только имя базы.

Правильный порядок теперь такой:
```bash
php artisan config:clear && php artisan test && php artisan config:cache
```

### 3.3. Логи росли без ограничений
`storage/logs/laravel.log` не ротировался — на долгом стенде это медленное
заполнение диска. **Исправлено:** `/etc/logrotate.d/numeros-es`, еженедельно,
8 копий, сжатие.

## 5. Открыто — обязательно перед боевым запуском

По твоему решению отложено до выката на прод; фиксирую, чтобы не потерялось.

1. **TLS отсутствует.** Сейчас HTTP, и пароль Basic Auth ходит открытым текстом.
   Перед продом — сертификат (Let's Encrypt), редирект 80→443, HSTS.
2. **SSH: вход root по паролю разрешён** (`PermitRootLogin yes`,
   `PasswordAuthentication yes`), а root-пароль и пароль панели netcup
   передавались открытым текстом в переписке. **Их нужно сменить**, а
   парольный вход отключить — доступ по ключу уже настроен и работает.
3. Нет фаервола (ufw), нет fail2ban, нет автоматических обновлений
   безопасности (`unattended-upgrades`). Для боевого сервера — обязательны.
4. `expose_php = On` — PHP светит версию в заголовках. Мелочь, но выключается
   одной строкой.

## 6. Расхождение, которое нужно решить осознанно

`CLAUDE.md` (инвариант №10 и раздел «Стек») описывает боевую площадку как
**Bluehost с MySQL 5.7.44**, рядом с чужим платёжным сайтом `cac.az`, — отсюда
запреты «ничего из MySQL 8», «не трогать `public_html`», «не запускать composer
на хосте».

Новый сервер клиента — **выделенный, чистый, с MySQL 8.0.46**, соседей нет.
Если боевой запуск будет здесь, а не на Bluehost, то:

- ограничение «ничего из MySQL 8» **снимается** (схема и так совместима —
  проверено: миграции легли на MySQL 8 без единой правки);
- запреты, связанные с соседством `cac.az`, **перестают действовать**;
- composer на хосте запускать можно (уже запускался при переносе), а вот
  Node на сервере по-прежнему нет — **ассеты собираются локально**.

Решение за клиентом. Пока оно не принято, документацию не переписывал:
`CLAUDE.md` и блюпринт остались как есть — это источники правды по решениям,
и менять их без явной просьбы нельзя.
